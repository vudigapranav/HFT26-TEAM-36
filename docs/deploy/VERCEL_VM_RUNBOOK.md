## Architecture (LOCKED, CLAUDE.md)

```text
browser ──HTTPS──▶ Vercel project (root: src/frontend, Vite static build)
                     ├─ static files (index.html, assets/, landing/)
                     └─ /api/:path*  ──Routing Middleware adds X-TorqueCode-Proxy──▶ rewrite https://<BACKEND_HOST>/:path*
                                                                                   │
                     VM: Caddy :443 (403 without the proxy secret) ──▶ Fastify 127.0.0.1:3001
                                                                        ├─ PostgreSQL 16 (127.0.0.1)
                                                                        ├─ docker CLI → R3 worker + grader containers
                                                                        └─ api.featherless.ai
```

The browser only talks to the Vercel origin, so the session cookie is first-party (`__Host-tc_session`, Secure,
HttpOnly, SameSite=Lax). No CORS is added.

**A rewrite alone is not the security boundary.** The protections are:
1. Caddy refuses any request without `X-TorqueCode-Proxy: <secret>` (`deploy/cloud/Caddyfile`).
2. The Vercel middleware (`deploy/cloud/vercel/middleware.ts`) deletes every client-sent forwarding header and any
   client-sent `x-torquecode-proxy`, then sets the client IP only from Vercel's `ipAddress(request)` and adds the secret.
3. The backend trusts exactly one forwarding hop only when `TRUST_PROXY=true` (`src/backend/api/config.ts`). This is on
   main since K11 (#56). The note in `deploy/cloud/README.md` and `backend.env.example` saying "not on main yet" is stale
   (Rithvik's files; tell him to update them).

## Vercel project settings (checked against vercel.com/docs on 31 Oct 2026)

- **Root Directory:** `src/frontend`. Vercel reads `vercel.json` from the project's root directory and detects pnpm from the
  lockfile at the repository root (`pnpm-lock.yaml`; `pnpm-workspace.yaml` already lists `src/frontend` and
  `src/backend/contracts`).
- **Framework preset:** Vite. **Output directory:** `dist`.
- **Install command:** `pnpm install --frozen-lockfile --ignore-scripts` (filtered alternative from the monorepo docs:
  `pnpm install --frozen-lockfile --ignore-scripts --filter torquecode-frontend...`).
- **Build command:** `pnpm run build` (the frontend script already runs `pnpm --filter @torquecode/contracts build`
  before `tsc -b && vite build`, on PR #59).
- Node 24 (project setting).
- The app uses a hash router (`/#/login`), so deep links don't need the SPA fallback. It's kept for any other path.
  Vercel serves existing static files before applying rewrites.
- External rewrites honour upstream `Cache-Control` by default on projects created after 6 Apr 2026. Auth responses
  already send `no-store`; to be safe, disable rewrite caching for `/api` (header below).

### `src/frontend/vercel.json` (TEMPLATE: do not commit until `<BACKEND_HOST>` is real)

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "framework": "vite",
  "installCommand": "pnpm install --frozen-lockfile --ignore-scripts",
  "buildCommand": "pnpm run build",
  "outputDirectory": "dist",
  "rewrites": [
    { "source": "/api/:path*", "destination": "https://<BACKEND_HOST>/:path*" },
    { "source": "/((?!api/|assets/|landing/).*)", "destination": "/index.html" }
  ],
  "headers": [
    { "source": "/api/:path*", "headers": [{ "key": "x-vercel-enable-rewrite-caching", "value": "0" }] }
  ]
}
```

### Middleware (adds the proxy secret)

Copy `deploy/cloud/vercel/middleware.ts` and `deploy/cloud/vercel/torquecode-proxy-headers.mjs` into `src/frontend/`
next to `package.json`, then `pnpm --filter torquecode-frontend add @vercel/functions` (lockfile changes; commit it).
Its unit tests: `node --test deploy/cloud/vercel/torquecode-proxy-headers.test.mjs`.

Alternative from the current Vercel docs ("Restricting your origin to Vercel traffic"): a `routes` transform with
`request.headers` `set` from an env var. It can't be mixed with `rewrites` in the same file, and it doesn't strip
client-sent forwarding headers, so keep the tested middleware unless it fails on the real deployment.

## Deploy order

1. VM: `git clone https://github.com/vudigapranav/HFT26-TEAM-36.git /opt/torquecode`, then
   `BACKEND_HOST=… ACME_EMAIL=… AUTH_ORIGIN=https://<vercel-app> ADMIN_SSH_CIDR=… bash /opt/torquecode/deploy/cloud/setup-vm.sh`.
   Add `FEATHERLESS_API_KEY`, the two model variables and `TRUST_PROXY=true` to `/etc/torquecode/backend.env`;
   `systemctl restart torquecode-backend`. Note the printed proxy secret.
2. On the VM: `curl -fsS http://127.0.0.1:3001/health` shows `"runner_available":true`.
3. Vercel: create the project (settings above), set `TORQUECODE_PROXY_SECRET`, add `vercel.json` + middleware on a
   `pranav/deploy-vercel` branch, deploy a preview, then promote to production.
4. If the production URL differs from the `AUTH_ORIGIN` you used, fix `AUTH_ORIGIN` on the VM and restart.

## Rollback

- **Frontend:** in Vercel, Deployments → previous production deployment → "Promote to Production" (instant).
- **Backend:** on the VM, `cd /opt/torquecode && sudo -u torquecode git checkout <previous-good-sha> && sudo -u torquecode npx -y pnpm@11.25.0 install --frozen-lockfile --ignore-scripts && sudo -u torquecode npx -y pnpm@11.25.0 build && systemctl restart torquecode-backend`.
  Migrations are forward-only and checksummed: take a `pg_dump` (command in `deploy/cloud/README.md`) **before** any
  deploy that adds a migration, and restore it if you roll back across one.
- **Secret leak:** `ROTATE_PROXY_SECRET=1 bash deploy/cloud/setup-vm.sh`, update Vercel's `TORQUECODE_PROXY_SECRET` and
  redeploy at once (requests get 403 in between).
- **Demo fallback:** run locally with `deploy/start.sh` + the Vite dev server, plus the backup recording (docs/demo/DEMO_CHECKLIST.md).
